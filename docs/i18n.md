# Internationalization (EN / KM)

NOBLE STRIKE supports English and Khmer. There is no locale URL prefix
(`/en/...`, `/km/...`) — the same URL renders in whichever language the
visitor has selected, tracked via a cookie. This document covers the three
places translation lives in this codebase and how to extend each one.

1. UI strings (`next-intl`) — everything rendered by React components.
2. Bilingual CMS content (`_en`/`_km` column pairs) — News, Tournaments,
   Legacy Events.
3. The Telegram bot's own small locale dictionary — it isn't React, so it
   doesn't use next-intl.

---

## 1. UI strings — architecture

- Library: [`next-intl`](https://next-intl.dev), configured without its
  routing/middleware URL-prefix feature. `src/i18n/config.ts` defines the
  supported locales:

  ```ts
  export const locales = ["en", "km"] as const;
  export const defaultLocale: Locale = "en";
  export const localeCookieName = "ns_locale";
  ```

- **Where the active locale comes from**: on the **server**,
  `src/i18n/request.ts` reads the `ns_locale` cookie on every request
  (`getRequestConfig`) — this feeds every Server Component's
  `getTranslations()`. On the **client**, `src/components/i18n/i18n-provider.tsx`
  owns the active locale in React state (seeded from that same cookie value on
  first paint, so SSR and hydration agree) and feeds every Client Component's
  `useTranslations()` / `useLocale()`. There's no `[locale]` route segment, so
  `next-intl`'s routing middleware isn't used at all here.

- **English fallback via deep merge**: `locales/km.json` is not required to
  be complete. `mergeMessages()` (`src/lib/i18n/merge.ts`, shared by the
  server request config and the client provider so both build an identical
  tree) deep-merges the Khmer message tree over the English one, key by key,
  recursively — any key present in `en.json` but missing (or not yet
  translated) in `km.json` silently falls back to its English text. Add a new
  key to `en.json` alone and ship it; Khmer catches up later without breaking
  anything. The merge runs once at module load, not per request.

- **Switching is instant (client-side, in-memory)**: `src/components/i18n/
  i18n-provider.tsx` bundles **both** dictionaries into the client and builds
  both merged trees at module load. `LanguageSwitcher` calls the provider's
  `setLocale()`, which (1) swaps the in-memory dictionary via `setState` —
  only `useTranslations`/`useLocale` consumers re-render, no network, no
  `router.refresh()` on the critical path — then (2) off the critical path,
  persists the `ns_locale` cookie (`src/app/actions/locale.ts`) and fires one
  low-priority `router.refresh()` inside a transition so any
  Server-Component-rendered text (dashboard/admin/news/legacy/detail pages)
  catches up. The public homepage is 100% client, so it switches with zero
  perceived delay.

- **Persistence — cookie + localStorage**: the cookie is the source of truth
  for server rendering. The provider also mirrors the choice into
  `window.localStorage` under the same key. On first paint it compares the
  server-rendered locale against `localStorage`; if they disagree (cleared
  cookies, a new device session) it adopts the stored preference — now an
  in-memory swap plus a background cookie sync, not a blocking refresh.

## Adding a new UI translation key

1. Add the key to **both** `locales/en.json` and `locales/km.json`, at the
   same nested path in each file. Keep the two files structurally
   identical — same nesting, same key names — even though `km.json` can
   temporarily hold an English placeholder for a string not translated yet
   (it'll render correctly either way thanks to the deep-merge fallback
   described above; the point of matching structure is so a future Khmer
   pass can find every key by diffing the two files).
2. Read it from a Server Component with `getTranslations`:

   ```ts
   import { getTranslations } from "next-intl/server";
   const t = await getTranslations("namespace");
   t("myKey");
   ```

   or from a Client Component (must be `"use client"`) with `useTranslations`:

   ```ts
   import { useTranslations } from "next-intl";
   const t = useTranslations("namespace");
   t("myKey");
   ```

   `"namespace"` is the top-level (or dotted nested) key path in the JSON
   files — e.g. the Telegram bot's reference copy lives under `"telegram"`,
   the locale-tabs admin widget under `"admin.localeTabs"`
   (`src/components/admin/locale-tabs.tsx`).
3. Do not hardcode English strings directly in JSX going forward — route
   anything user-facing through `t(...)`.

## 2. Bilingual CMS content (`_en`/`_km` column pairs)

Content tables that editors fill in through an admin form (News,
Tournaments, Legacy Events) don't use `next-intl` message files — they use a
column-pair convention directly in Postgres, added in
`supabase/migrations/0019_i18n_content.sql`:

| Table            | English column(s)                     | Khmer column(s)          |
|------------------|----------------------------------------|---------------------------|
| `news`           | `title_en`, `excerpt_en`, `content_en` | `title_km`, `excerpt_km`, `content_km` |
| `tournaments`     | `name_en`, `description_en`            | `name_km`, `description_km` |
| `legacy_events`  | `title_en`, `description_en`           | `title_km`, `description_km` |

The `_en` columns are `not null` (they're the renamed originals — no data
was lost in the migration). The `_km` columns are always **nullable and
optional**: Khmer content is a nice-to-have, not a requirement, for every
piece of CMS content.

- **Reading**: use `pickLocalized()` from `src/lib/i18n/content.ts`:

  ```ts
  import { pickLocalized } from "@/lib/i18n/content";
  const title = pickLocalized(newsRow, "title", locale); // "title" -> reads title_en / title_km
  ```

  It reads `${field}_en`/`${field}_km` off the row and falls back to the
  English value whenever the Khmer field is missing or blank (`km &&
  km.trim().length > 0 ? km : en`). This is the *only* place that fallback
  logic should live — don't reimplement it inline at a call site.

- **Editing**: admin forms present both language versions in one form using
  `<LocaleTabs>` (`src/components/admin/locale-tabs.tsx`) — an English tab
  and a Khmer tab over the same field pair, so the form doesn't have to grow
  a second visible copy of every input:

  ```tsx
  <LocaleTabs
    en={<Input name="title_en" defaultValue={item?.title_en} required />}
    km={<Input name="title_km" defaultValue={item?.title_km} />}
  />
  ```

  The Khmer tab also renders a small hint (`admin.localeTabs.khmerHint`)
  reminding the editor that leaving it blank is fine.

### Adding a new bilingual field to an existing table (or a new table)

1. Migration: add `<field>_en` (usually `not null` if it's required content)
   and `<field>_km` (always nullable) columns. Follow the naming used above
   — don't invent a different suffix convention.
2. Server: wherever you currently read the old single-language column,
   switch to `pickLocalized(row, "<field>", locale)`.
3. Admin form: wrap the English/Khmer inputs in `<LocaleTabs en={...}
   km={...} />` instead of two separately-labeled fields.
4. Any select/insert/update statement that referenced the old column name
   needs both `_en` and `_km` in its column list now.

## 3. Telegram bot locale dictionary

The bot lives entirely under `src/lib/telegram/` and
`src/app/api/telegram/webhook/route.ts` and is deliberately not built on
`next-intl` or React (see `src/lib/telegram/client.ts:1-10` for why the bot
itself is a thin hand-rolled wrapper, not a library like Telegraf/grammY —
same "no framework dependency for a single POST endpoint" philosophy applies
to its i18n). Instead, `src/lib/telegram/i18n.ts` exports a plain
`Record<'en'|'km', Record<key, string>>`:

```ts
export const TELEGRAM_DICTIONARY: Record<TelegramLocale, TelegramDictionary> = {
  en: { welcome: "...", help: "...", /* ... */ },
  km: { welcome: "...", help: "...", /* ... */ },
};

export function getTelegramLocale(locale: string | null | undefined): TelegramLocale {
  return locale === "km" ? "km" : "en";
}

export function tTelegram(locale: TelegramLocale, key: keyof TelegramDictionary): string {
  return TELEGRAM_DICTIONARY[locale][key];
}
```

This is the same `Record<Key, string>`-per-locale shape already used
elsewhere in the codebase for non-next-intl string tables (e.g.
`MLBB_ROLE_LABELS`/`HOK_ROLE_LABELS` in `src/lib/validation/team.ts`). The
English/Khmer copy for keys that are also referenced from the `"telegram"`
namespace in `locales/en.json`/`locales/km.json` is duplicated here
verbatim as literal strings — intentionally: those JSON files exist as the
readable source-of-truth copy for translators, but importing them at
runtime would pull `next-intl`'s message shape into server-only bot code
that has no other reason to depend on it. If you change the wording in one
place, change it in the other.

**Which locale a reply uses**: the webhook (`handleUpdate()` in
`src/app/api/telegram/webhook/route.ts`) has no Supabase Auth session —
Telegram calls it, not a signed-in browser — so it can't do a normal
RLS-guarded `select`. It looks up the linked profile's `locale` column via
`get_telegram_profile_locale(p_telegram_id)`, a `SECURITY DEFINER` RPC
added in `supabase/migrations/0020_telegram_locale_rpcs.sql` (same pattern
as the pre-existing `consume_telegram_link_token()` from
`0014_telegram_integration.sql`). A chat that hasn't run `/start` yet has no
linked profile row, so `getTelegramLocale(undefined)` defaults it to `'en'`.

**The `/language` command**: `/language en` or `/language km` calls
`set_telegram_profile_locale(p_telegram_id, p_locale)` (also in `0020`),
which updates `profiles.locale` for the profile linked to that chat — or
does nothing and returns no row if the chat isn't linked yet. Either way the
bot replies in the *requested* language; there's just nothing persisted for
an unlinked chat. `/language` with no argument replies with usage
instructions in the chat's *current* locale.

### Adding a new bot string

1. Add the key to the `TelegramDictionary` interface and both the `en` and
   `km` entries of `TELEGRAM_DICTIONARY` in `src/lib/telegram/i18n.ts`.
2. Call it from the webhook handler with `tTelegram(locale, "yourKey")`,
   where `locale` came from `getLocaleForChat()` (or a locale you already
   have in hand, e.g. right after `/language` changes it).
3. If the string is also meaningful as UI copy elsewhere (e.g. shown on a
   dashboard settings page describing what the bot will say), consider
   whether it belongs under the `"telegram"` namespace in
   `locales/en.json`/`locales/km.json` too — but the bot code itself must
   keep reading from `src/lib/telegram/i18n.ts`, not from next-intl.

## 4. Adding a third locale (future)

Not implemented, but if a third language were added later:

1. **`src/i18n/config.ts`**: add the new code to `locales` (and update
   `LocalePreference` in `src/lib/types/database.ts` and the
   `profiles.locale` check constraint in a new migration — it's currently
   `check (locale in ('en', 'km'))`).
2. **`locales/en.json` / `locales/km.json`**: add `locales/<code>.json`
   with the same key structure as the other two. Both the `MESSAGES` map in
   `src/i18n/request.ts` and the one in `src/components/i18n/i18n-provider.tsx`
   would need a `<code>: mergeMessages(en, <code>)` entry (and the provider
   would import and bundle the new dictionary).
3. **`src/components/ns/language-switcher.tsx`**: the button list is
   currently a hardcoded `(["en", "km"] as const).map(...)` with an inline
   `code === "en" ? "EN" : "ខ្មែរ"` label — both would need to iterate
   `locales` from config and use a label lookup instead of the ternary.
4. **Bilingual CMS content**: every `_en`/`_km` column pair (News,
   Tournaments, Legacy Events) would need a third `_<code>` column, and
   `pickLocalized()` in `src/lib/i18n/content.ts` would need a fallback
   chain (`<code> → en`) instead of the current binary
   `km ?? en`. `<LocaleTabs>` would need a third tab.
5. **Telegram bot**: add the new locale to `TelegramLocale` and
   `TELEGRAM_DICTIONARY` in `src/lib/telegram/i18n.ts`, and extend the
   `/language` argument parsing (currently `arg !== "en" && arg !== "km"`)
   in the webhook handler.
